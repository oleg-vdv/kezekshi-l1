# kezekshi-l1: руководство оператора SOC

Как развернуть локальную ИИ-модель L1-триажа, подключить её к Wazuh, и как
дежурный аналитик с этим работает: что система закрывает сама, что попадает к
человеку и как это разбирать. Инструмент читает Wazuh только на чтение и ничего
в нём не меняет.

---

## 1. Что это и как устроено

Модель `kezekshi-l1` (дообученная Gemma 4 E2B, работает офлайн через Ollama)
разбирает алерты Wazuh как аналитик первой линии: отсеивает шум и готовит по
подозрительному краткую карточку для второй линии (L2).

```
   Wazuh Indexer (только чтение)
            |
            v
   [1] fast-path памятки ──► операционный шум ──► АВТО-ЗАКРЫТО (в журнал аудита)
            |                   (без вызова модели, ~85-95% потока)
            v
   [2] модель kezekshi-l1 ──► карточка (вердикт, MITRE, обоснование)
            |
            v
   [3] политика маршрутизации ──► очередь L2 (out/l2_queue.jsonl)
            |
            v
   дежурный аналитик: analyst.py  ──►  диспозиция (out/dispositions.csv)
```

Два яруса: дешёвый детерминированный fast-path закрывает известный шум без
модели; модель включается только на неоднозначном «хвосте». Это экономит вызовы
модели и даёт предсказуемость.

Четыре класса вердикта:

| класс | смысл | что делать |
|---|---|---|
| `false_positive` | сработка ошибочна / штатная работа | закрыть |
| `benign_true_positive` | событие реальное, но легитимное | закрыть |
| `suspicious` | возможная атака без подтверждённого успеха | разобрать (L2) |
| `incident_candidate` | подтверждённый успех / компрометация | реагирование (IR) |

## 2. Развёртывание с нуля

### 2.1. Бокс с моделью (GPU-машина с Ollama)

Нужны: установленный [Ollama](https://ollama.com) и файл весов
`kezekshi-l1-v5.1-q8_0.gguf` (~4.9 ГБ) с `Modelfile.v5.1`.

```bash
ollama create kezekshi-l1-v5.1 -f Modelfile.v5.1
ollama list
```

Чтобы Ollama слушал по сети (pipeline ходит на него с другого хоста) и поднимался
сам после перезагрузки:

```bash
setx OLLAMA_HOST "0.0.0.0:11434"
```

Проверка, что модель отвечает:

```bash
ollama run kezekshi-l1-v5.1 "привет"
```

Веса не в репозитории (большие). Их собирают из LoRA-адаптера скриптами
`src/merge_hf.py` + `llama.cpp/convert_hf_to_gguf.py` (см. `docs/dataset.md`).

### 2.2. Хост pipeline (где крутится триаж)

Это машина с доступом к Wazuh Indexer и к боксу Ollama. Может быть тем же боксом.

1. Python 3.11+ и репозиторий `kezekshi`.
2. Зависимости: `pip install -r requirements.txt`.
3. Эндпоинт Ollama задан в `src/triage.py` (`OLLAMA = "http://<бокс>:11434/api/chat"`).
   Если бокс по другому адресу - поправить тут.
4. Доступ к Wazuh (раздел 3).
5. Конфиг режима (переменные среды, см. раздел 5):

```bash
setx KEZEKSHI_AUTOCLOSE assist
setx TRIAGE_THINK 0
```

Разовая проверка без службы (один проход по новым алертам):

```bash
cd C:\kezekshi\pipeline
python run.py --once
```

### 2.3. Служба автозапуска

Демон (`run.py --interval 30`) опрашивает Wazuh каждые 30 с. Чтобы он поднимался
сам, он оформлен задачей Планировщика Windows `KezekshiL1`, которая запускает
`pipeline\run_daemon_assist.bat` при входе пользователя. Пересоздать задачу:

```powershell
$a = New-ScheduledTaskAction -Execute "C:\kezekshi\pipeline\run_daemon_assist.bat"
$t = New-ScheduledTaskTrigger -AtLogOn -User "HOST\soc"
$s = New-ScheduledTaskSettingsSet -ExecutionTimeLimit ([TimeSpan]::Zero) -MultipleInstances IgnoreNew -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 1) -StartWhenAvailable
$p = New-ScheduledTaskPrincipal -UserId "HOST\soc" -LogonType Interactive -RunLevel Limited
Register-ScheduledTask -TaskName "KezekshiL1" -Action $a -Trigger $t -Settings $s -Principal $p -Force
Start-ScheduledTask -TaskName "KezekshiL1"
```

Триггер - вход пользователя (не чистая загрузка без логина). Запуск от SYSTEM на
boot не используется: он бы потерял пользовательские секреты и переменные среды.
Лог демона: `pipeline\out\daemon_service.log`. Запускать строго один экземпляр
(два процесса будут дублировать разбор).

## 3. Подключение к Wazuh

Pipeline ходит в Wazuh Indexer (OpenSearch) только на чтение: `_search` и
`_count`, ничего не пишет.

1. Создать в Wazuh учётку только для чтения (напр. `kezekshi-ro`) с правом читать
   индексы `wazuh-alerts-*`.
2. Положить доступ в `~/.kezekshi/wazuh.env` (под ACL, не в репозиторий):

```
WAZUH_INDEXER_USER=kezekshi-ro
WAZUH_INDEXER_PASS=<пароль>
```

3. Адрес индексатора - переменная `WAZUH_INDEXER_HOST` (по умолчанию
   `https://10.0.0.28:9200`).

Проверка связи:

```bash
cd C:\kezekshi\pipeline
python -c "import sys; sys.path.insert(0,'.'); import wz; print(wz.q('/wazuh-alerts-*/_count',{'query':{'match_all':{}}})['count'], 'алертов')"
```

## 4. Фазы внедрения

Вводить постепенно - это снижает риск и даёт собрать эталон смены.

- **Фаза 1 (тень):** `KEZEKSHI_AUTOCLOSE=off`. Система ничего не закрывает, только
  пишет карточки. Дежурный работает как раньше и сверяется.
- **Фаза 2 (ассист) - ТЕКУЩАЯ:** `KEZEKSHI_AUTOCLOSE=assist`. Сам закрывается
  только детерминированный шум из белого списка памятки. Всё, что дошло до
  модели, уходит человеку с карточкой. **Модель не закрывает ничего** - нулевой
  риск, разгрузка L1 на шуме.
- **Фаза 3 (авто):** `KEZEKSHI_AUTOCLOSE=rulebook`. Модель начинает авто-закрывать
  и часть хвоста. Переходить только после дообучения на реальных диспозициях
  смены (раздел 8) и проверки точности/полноты.

---

## 5. Как закрываются алерты

Каждое решение пишется в журнал аудита `pipeline\out\audit.jsonl`. Два исхода:
`auto_close` (закрыл L1) и `to_L2` (человеку).

**Что L1 закрывает сам (fast-path, без модели):** высокочастотный операционный
шум из белого списка памятки `src/rulebook.py` - ротация реестра/файрвола,
ошибки приложений Windows, служебные события Wazuh, штатные события Linux,
замечания rootcheck на слоях Docker и т.п. Контекст памятки при этом НЕ пускает
в авто-закрытие опасные под-случаи (ключи автозапуска, rootkit, критичные пути
`/etc/*`, защитные службы, признаки шифровальщика в FIM) - они дают `suspicious`.

**Что уходит человеку (L2):** всё остальное - вход/подбор/новые пользователи,
sudo, срабатывания высокого уровня, а также любой ответ модели, не прошедший
валидатор (выдуманный IP/хеш, claim без доказательства, пустой ответ) и любой
текст в логах, похожий на инъекцию-инструкцию.

**В Фазе 2 модель не закрывает ничего:** если алерт дошёл до модели, он идёт на
L2 с её карточкой, даже если модель назвала его `benign`. Так единственное, что
закрывается само, - заведомый шум.

**Инцидент никогда не закрывается автоматически** ни в одной фазе.

## 6. Рабочее место аналитика (analyst.py)

Очередь L2 - это файл `pipeline\out\l2_queue.jsonl`. Разбирать её удобно
инструментом `analyst.py` (ничего в Wazuh не пишет, работает по локальным файлам).

Если в консоли кириллица «кракозябрами» - один раз в сессии: `chcp 65001`.

**Посмотреть открытые тикеты:**

```bash
cd C:\kezekshi\pipeline
python analyst.py list
```

```
Открытых тикетов: 13

ID             правило возраст  вердикт модели       хост / суть
----------------------------------------------------------------------------
1793268174.200   40101     44м  suspicious           10.0.8.8 | У учётной записи 'user' вошёл с внешнего IP ...
fLYzh6EBcrC4Zt    5710     44м  suspicious           10.0.0.28 | Попытки входа по SSH с несуществующим ...
...
```

**Открыть карточку тикета** (можно короткий префикс ID):

```bash
python analyst.py show 1793268174.200
```

Карточка показывает: вердикт модели и памятки, суть, утверждения со ссылками на
конкретные доказательства `[E13, E18]`, техники MITRE, чего не хватает и что
проверить, плюс служебную строку (уровень, валидатор).

**Закрыть тикет с диспозицией** (ваш вердикт - эталон смены):

```bash
python analyst.py close 1793268174.200 suspicious -n "перебор по списку, заблокировал IP" -m T1110.001 -a oleg
```

Вердикт - один из `false_positive | benign_true_positive | suspicious |
incident_candidate`. Флаги: `-n` причина (1 строка, по сути), `-m` техника MITRE,
`-a` имя аналитика (иначе - из `%USERNAME%`). Тикет уходит из списка открытых,
запись добавляется в `pipeline\out\dispositions.csv`.

**Если это инцидент** (`incident_candidate`): L1-триаж на этом заканчивается -
заводите реагирование (IR) по вашему регламенту: изоляция узла, сбор артефактов,
эскалация. Инструмент это подскажет, но сам реагирование не ведёт.

## 7. Ежедневная рутина дежурного (чеклист)

1. **Служба жива?**

```powershell
Get-ScheduledTask -TaskName KezekshiL1 | Select State
```

2. **Суточный отчёт** (сколько закрыто/на L2, топ шумовых правил, шумные узлы):

```bash
python run.py --report
```

3. **Разобрать очередь:** `python analyst.py list`, затем по каждому `show` и
   `close`. Приоритет - `incident_candidate` и `suspicious` высокого уровня.
4. **Спорное** (модель и памятка разошлись, или валидатор поднял) - смотреть
   внимательнее: в карточке видно, на что опиралась модель.

## 8. Эксплуатация службы

```powershell
Get-ScheduledTask -TaskName KezekshiL1 | Select State     # статус
Stop-ScheduledTask  -TaskName KezekshiL1                  # остановить
Start-ScheduledTask -TaskName KezekshiL1                  # запустить
Disable-ScheduledTask -TaskName KezekshiL1                # снять с автозапуска
```

Логи: `pipeline\out\daemon_service.log` (демон), `audit.jsonl` (все решения),
`l2_queue.jsonl` (очередь). Мониторить стоит: жив ли процесс, доступны ли Wazuh и
Ollama, не растёт ли необработанная очередь L2. Демон переживает перезапуск -
место в потоке хранит `out\state.json` (чекпоинт после каждого алерта).

## 9. Сбор эталона и переход к Фазе 3

`dispositions.csv` - это журнал разбора И эталон смены для дообучения следующей
версии модели. Чем больше реальных диспозиций (особенно по спорному и по редким
атакам), тем честнее будущие метрики. Когда накопится достаточно (ориентир -
десятки реальных атак и сотни разборов), на этих данных дообучается v6, и только
после проверки её точности и полноты имеет смысл переходить к Фазе 3
(`KEZEKSHI_AUTOCLOSE=rulebook`), где модель начинает закрывать часть хвоста.

Важно: текущая модель обучена на синтетике плюс прокси-разметке; полнота
обнаружения на реальных атаках ещё не измерена. Поэтому Фаза 2 (модель ничего не
закрывает) - безопасный режим по умолчанию.

## 10. Диагностика

| Симптом | Причина / что делать |
|---|---|
| в консоли кракозябры | `chcp 65001` перед запуском |
| очередь L2 растёт, разбора нет | проверить, жив ли дежурный процесс разбора; это нормально, если смены нет |
| все тикеты «нет ответа модели» | недоступен Ollama-бокс; проверить `ollama list` на боксе и сеть |
| `python run.py --once` падает на Wazuh | проверить `wazuh.env`, адрес `WAZUH_INDEXER_HOST`, сеть до `:9200` |
| служба не стартовала после перезагрузки | триггер - вход пользователя: нужно залогиниться под учёткой задачи |
| демон запущен дважды | оставить один экземпляр (Планировщик + ручной запуск конфликтуют) |

---

## 11. Границы и безопасность

- Wazuh только на чтение (`_search`/`_count`); система в нём ничего не меняет и не
  закрывает алерты в самом Wazuh - только в своём журнале и очереди.
- Секреты (`wazuh.env`) под ACL, не в репозитории. Ollama без аутентификации -
  не выставлять в недоверенную сеть.
- Инцидент автоматически не закрывается никогда.
- Публикация репозитория/модели - решение владельца, не часть эксплуатации.
